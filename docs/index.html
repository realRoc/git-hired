STEP 01 ／ 06

从一个 Issue 开始ISSUE · 提出问题

一切从一个 Issue 开始。先用一两句话把"为谁解决什么"写清楚——能讲明白的需求，才值得进入下一步。Issue 是这次工作的起点，也会是它最后的归处。

STEP 02 ／ 06

进入开发沙盒SANDBOX · 持续的开发环境

沙盒就是我们的开发环境，长期运行、随时可用。它不是一次性的临时容器——它保留依赖、缓存与既有数据，让 AI 能在真实的上下文里工作，而不是从零开始。

STEP 03 ／ 06

执行任务 · 发起 PREXECUTE · Claude Code 或 Codex

把 Issue 交给 Claude Code 或 Codex，由它在沙盒里完成具体的实现：写代码、跑测试、迭代修复。完成之后，它会把分支 push 到远程并发起一份 PR——这次工作的交付，到这里才算落地。

STEP 04 ／ 06

由另一位 AI 审核 PRAI REVIEW · 双 AI 互审

这一步交给另一位 Claude Code 或 Codex 来做。它读完整份 PR，结合 CI 与静态检查的结果，给出可执行的修改意见——双 AI 互审，让显性问题在这里就被拦下来，再进入人类的视野。

STEP 05 ／ 06 · 关键一步

人类架构师评审ARCHITECT REVIEW · 专家把关

这一步是整条流程的核心。由人类专家架构师来判断这次改动是否符合系统的方向、是否引入隐性债务、是否值得上线。AI 提供线索，决定权始终落在人身上——架构师的签字，是这次改动真正的通行证。

STEP 06 ／ 06

合并并上线PRODUCTION · 正式发布

架构师签字之后，PR 合入主干、部署到生产环境。这一次的决定与产物——可复用的 Skill、Checklist、评审记录——都会回写到 Issue 上，留给下一次接手的人。

# 留下可被下一次工作复用的痕迹
§ 02 RITUALS

流水线之外，
那些让协作成立的小习惯.

流程负责"做什么"，习惯负责"在什么节奏里做"。下面这四件事，是我们用来让 AI-native 协作真正运转起来的最小集。

RITUAL · 01

一日的形状THE SHAPE OF A DAY

每天早晨花一分钟，写下今天最重要的那个 Issue。它不是任务清单，而是这一天的锚点——所有的对话、改动、PR，都围绕它发生。

  • MORNING写下 #today —— 当日最重要的 Issue
  • DURING所有改动都挂在这条 Issue 下面
  • EVENING用一句话回写今天的进展或决定
RITUAL · 02

架构师与开发者ARCHITECT & DEVELOPERS

架构师拥有方向上的最终决策权；开发者围绕 Issue 进行开发，通过 Issue 与 PR 与架构师对话。评审与决策落在 GitHub 上，飞书留给当下需要立刻对齐的事。

  • ARCHITECT方向与边界的最终决策权
  • DEVELOPER围绕 Issue 开发 · 在 PR 中对话
  • CHANNEL评审在 GitHub · 即时同步在飞书
RITUAL · 03

Issue 与 PR 的追踪EVERY ISSUE IS TRACKED

每一个 Issue 都有一条对应的 PR 来追踪它的执行过程，PR 上的评论会被完整保留下来——下一个接手的人，可以从 Issue 一路读到当时是怎么决定的。

  • LINK每个 Issue 对应一条 PR · 一一映射
  • KEEPPR 评论作为决策记录长期保留
  • READ新成员从 Issue → PR 还原历史
RITUAL · 04

从 Prompt 到 SkillFROM PROMPT TO SKILL

一份 Prompt 被反复用过、值得保留下来，就会被沉淀成一个 Skill——带名字、带说明、可被引用。Skill 是团队真正在沉淀的工件。

  • SKILLreview · sandbox · rollback · architect-brief
  • CHECKfirst-pr · oncall-handover · post-incident
  • USAGE在 Claude Code 或 Codex 中通过 /use 调用
