What is GitHire · 一句话

GitHire 是一套 AI-native 入职与招聘工作流，让候选人和新人 在两周内交付真实生产 PR。

01 Issue-first
所有任务从一个能讲明白的 Issue 起步，需求即文档。
02 AI co-pilot
Sandbox 探索、PR 编写、Review 全程由 AI agent 辅助，人类 own merge。
03 Production-bound
终点是合并进主分支的 PR，不是 demo、不是练习题。

STEP 01 ／ 06

从一个
Issue 开始.

用一两句话把『为谁解决什么』写清楚——能讲明白的需求，才值得进入下一步。Issue 是这次工作的起点，也会是它的归档。

ISSUE · Frame the problem.

STEP 02 ／ 06

进入开发
沙盒.

沙盒是长期运行的开发环境，保留依赖、缓存与既有数据，让 AI 能在真实的上下文里工作，而不是一次性容器。

SANDBOX · A persistent dev environment.

STEP 03 ／ 06

执行任务
发起 PR.

把 Issue 交给 Claude Code 或 Codex，由它在沙盒里完成实现：写代码、跑测试、迭代修复，最终发起一份 PR。

EXECUTE · Claude Code or Codex.

STEP 04 ／ 06

另一位 AI
审核 PR.

这一步交给另一位 Claude Code 或 Codex。它读完整份 PR，结合 CI 与静态检查，给出可执行的修改意见——双 AI 互审。

AI REVIEW · Two agents, one PR.

STEP 05 ／ 06 · 关键一步

人类
架构师 评审.

整条流程的核心。由人类架构师判断这次改动是否符合系统方向、是否引入隐性债务、是否值得上线。AI 提供线索，决定权在人。

ARCHITECT · Where humans decide.

STEP 06 ／ 06

合并
并 上线.

架构师签字之后，PR 合入主干、部署到生产。可复用的 Skill、Checklist、评审记录回写到 Issue，留作下一次的起点。

PRODUCTION · Ship it.

— RITUALS

流水线之外，
那些让协作成立的小习惯.

流程负责"做什么"，习惯负责"在什么节奏里做"。下面这四件事，是我们用来让 AI-native 协作真正运转起来的最小集。

  • RITUAL · 01

    一日的形状

    THE SHAPE OF A DAY

    每天早晨花一分钟，写下今天最重要的那个 Issue。它不是任务清单，而是这一天的锚点——所有的对话、改动、PR，都围绕它发生。

    MORNING
    写下 #today —— 当日最重要的 Issue
    DURING
    所有改动都挂在这条 Issue 下面
    EVENING
    用一句话回写今天的进展或决定

  • RITUAL · 02

    架构师与开发者

    ARCHITECT & DEVELOPERS

    架构师拥有方向上的最终决策权；开发者围绕 Issue 进行开发，通过 Issue 与 PR 与架构师对话。评审与决策落在 GitHub 上，飞书留给当下需要立刻对齐的事。

    ARCHITECT
    方向与边界的最终决策权
    DEVELOPER
    围绕 Issue 开发 · 在 PR 中对话
    CHANNEL
    评审在 GitHub · 即时同步在飞书

  • RITUAL · 03

    Issue 与 PR 的追踪

    EVERY ISSUE IS TRACKED

    每一个 Issue 都有一条对应的 PR 来追踪它的执行过程，PR 上的评论会被完整保留下来——下一个接手的人，可以从 Issue 一路读到当时是怎么决定的。

    LINK
    每个 Issue 对应一条 PR · 一一映射
    KEEP
    PR 评论作为决策记录长期保留
    READ
    新成员从 Issue → PR 还原历史

  • RITUAL · 04

    从 Prompt 到 Skill

    FROM PROMPT TO SKILL

    一份 Prompt 被反复用过、值得保留下来，就会被沉淀成一个 Skill——带名字、带说明、可被引用。Skill 是团队真正在沉淀的工件。

    SKILL
    review · sandbox · rollback · architect-brief
    CHECK
    first-pr · oncall-handover · post-incident
    USAGE
    在 Claude Code 或 Codex 中通过 /use 调用

FAQ · 关于人月神话与 AI 协作

软件工程的老问题，AI 没让它们消失——只是换了形状。

进度落后的团队是否需要再加人？

不一定。新加的人需要时间学习上下文，沟通成本也会随人数二次方增长，因此短期内整体进度往往更慢——这就是 Brooks's Law。GitHire 的做法是把 Issue 上下文、Sandbox 探索、AI Review 报告全部沉淀为可读资产，让新人入场成本可控；只有当任务本身可拆分、上下文已结构化时，加人才有意义。

『人月』是个伪命题吗？

至少是一个粗暴的近似。软件工作不是体力劳动，人和月不可线性互换：复杂任务的依赖链限制了并行度，沟通成本随人数二次方增长，新成员的学习成本要从老成员的时间里扣。GitHire 不使用『人月』做估算，而是把工作拆为 Issue → PR 的可观测单元，用历史吞吐数据滚动预测。

原型是否一定要被丢掉？

Brooks 的建议是 Plan to throw one away; you will, anyhow——第一版的真正价值在于澄清问题。GitHire 把这条建议显式化：Sandbox 阶段产生的代码默认不进主分支，存在的目的是验证方向、暴露未知，而非交付。

Conceptual integrity 怎么在 AI 协作下保持？

通过显式的架构 owner。AI agent 可以生成 PR，但 Architect 这一步由人类负责。所有 PR 必须能被一位 architect 用一句话讲清楚动机和取舍——做不到的 PR 不 merge。这条约束让概念一致性不被并发的 agent 数量稀释。

为什么文档永远写不完？

因为写完即过时。GitHire 的策略是少写『文档』、多留『证据』：Issue 描述、PR diff、AI Review 报告、生产日志本身就是可追溯的文档链，自动按时间序拼成项目史，新人读这条链就能复现一次完整的决策过程。

Deadline 为什么总是骗人的？

因为估算是在信息最少的时候做的，承诺是在压力最大的时候许的。GitHire 用滚动 forecast 替代固定 deadline：每个 PR merge 之后基于真实吞吐重新预测，可观测的数据替代主观承诺，越接近交付，预测越收敛。
